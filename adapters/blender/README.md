# Blender adapter

The offline typed-operation runner uses Blender's official `--background --python` entry point. It generates a closed script from validated scene operations, requires a separate `.blend` output for edits, and never executes model-supplied Python. A live add-on bridge also exists (`comptrol_live_bridge.py`): it runs an authenticated loopback socket inside the already-open Blender process, queues every bpy mutation through `bpy.app.timers` onto Blender's main thread, and reports live readback. Both routes expose object inspection, common mesh primitives, transforms, basic Principled material values, object deletion, project save, and frame/still render.

The `blender.scene.copy_2d_rocket_to_3d` operation is available in the offline runner and live bridge. It only accepts a saved, clean source `.blend` with the expected rocket mesh names, requires a new output path, checks the source hash, makes a separate extruded copy, and reopens that copy before reporting geometry contact readback. An existing output is never overwritten. This conversion currently validates the named rocket layout; it is not a general-purpose 2D-to-3D converter. Saved outputs and render images are checked for nonzero size, while geometry readback—not process exit or file size alone—establishes conversion success.

For the live bridge, set `COMPTROL_BLENDER_BRIDGE_SOCKET` and `COMPTROL_BLENDER_BRIDGE_TOKEN` in the Blender process environment before starting the bridge. On Windows the bridge binds authenticated loopback TCP and writes the resolved endpoint to `COMPTROL_STATE_DIR/bridges/blender.json` (or `~/.comptrol/bridges/blender.json` when no state directory is supplied). `COMPTROL_BLENDER_BRIDGE_ENDPOINT`, when supplied to the client, is the connection endpoint; the socket setting is only the requested bind-path input and must not be used as the Windows TCP endpoint.
